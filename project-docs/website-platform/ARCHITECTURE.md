# Website Architecture

## Overview

The Cassady Tech Solutions website is an Astro application deployed to Cloudflare Workers. GitHub stores the source code and deployment configuration. Wrangler builds and deploys the Worker. Cloudflare serves both static site assets and server-side application logic.

## Repository

The repository is the source of truth for application code and version-controlled Cloudflare deployment configuration.

## Application Stack

The application uses:

- Astro 5
- TypeScript
- `@astrojs/cloudflare`
- MDX support
- Astro sitemap integration
- Wrangler 4
- Node.js 22 or newer for the local toolchain

The Astro configuration sets the canonical site to:

```text
https://cassadytech.com
```

The Cloudflare adapter is enabled so the application can run on Cloudflare Workers.

## Cloudflare Runtime

The Worker service is named:

```text
cassady-tech-site
```

The Worker entry point generated by the Astro build is:

```text
./dist/_worker.js/index.js
```

Static assets are served from:

```text
./dist
```

through the Cloudflare binding:

```text
ASSETS
```

The configured compatibility flag is:

```text
nodejs_compat
```

The repository currently contains both `wrangler.toml` and `wrangler.json`. Administrators should treat the effective Wrangler configuration used by the current deployment workflow as authoritative and avoid introducing conflicting settings between configuration files.

The custom domains provide the normal production experience. The `workers.dev` URL is the direct Cloudflare Worker endpoint and can be useful for troubleshooting or deployment validation.

## Request Flow

A standard request follows this path:

1. A visitor requests `cassadytech.com` or `www.cassadytech.com`.
2. DNS and Cloudflare route the request to the deployed Worker.
3. The Worker serves either the appropriate static asset or Astro-generated response.
4. Cloudflare returns the response from its edge network.

## Contact Form Architecture

The repository contains a server-side contact handler at:

```text
functions/api/contact.js
```

The handler accepts POST requests, reads JSON or form-encoded submissions, sanitizes fields, checks a honeypot field, validates Cloudflare Turnstile when configured, and sends the message through Resend.

Expected user-provided fields include:

- name
- email
- phone
- company
- service
- message

The endpoint also processes the `cf-turnstile-response` token when Turnstile is enabled.

## Trust Boundaries

Important trust boundaries include:

1. Browser to Cloudflare edge.
2. Cloudflare Worker to Turnstile verification service.
3. Cloudflare Worker to Resend API.
4. GitHub repository to deployment tooling.
5. Human administrator to GitHub, Cloudflare, and Resend administrative consoles.

Secrets must not cross into the public Git repository.

## Source of Truth Boundaries

GitHub is authoritative for:

- application source
- build scripts
- Wrangler configuration committed to the repository
- project documentation

Cloudflare is authoritative for runtime state that is not safe or practical to store in Git, including:

- Worker secrets
- custom-domain bindings
- account-level access
- Cloudflare-side service configuration

Resend is authoritative for:

- API credentials
- sender-domain verification
- service-side email configuration

## Design Intent

The architecture intentionally minimizes server ownership. There is no traditional web server or VM to patch for the public website. Application code is version controlled in GitHub and executed on Cloudflare's managed edge runtime.
